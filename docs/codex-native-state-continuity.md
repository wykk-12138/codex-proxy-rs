# Codex 二开目标：跨账号的 history/notes 连续性

> 状态：源码已按[架构说明](codex-native-state-continuity-plan.md)实现，个人单实例核心链路已验收；未部署，不代表全仓测试全绿
> 本文定义问题、能力边界与个人用途验收范围；接口与用法见 [API 参考](api.md#原生-codex-入口)，运行结果见[验收报告](reports/codex-native-state-continuity-acceptance.md)

## 核心目标

同一个 Codex 会话使用上游账号 A 时产生的 history 与 notes，在 A 推理额度耗尽、执行账号切换到 B 后仍然可用

B 必须能够通过官方 history/notes 工具检索早期历史、读取和修改原来的笔记；后续换上下文窗口、压缩和网关重启后仍能恢复这些状态。客户端继续使用同一个逻辑会话，不要求用户新建会话或手工复制资料

**这项二开解决的是原生状态连续性，不是普通模型请求的账号轮换，也不是单纯重放当前有效上下文**

“继承”按客户端可观察的能力判断：状态可以物理迁移，也可以保留在原位置并由网关正确路由访问。方案必须说明其依赖，不能把“暂时还能访问原账号”冒充原账号永久失效后仍可恢复

## 功能要求

| 对象 | 切换执行账号后应保持的能力 |
| --- | --- |
| notes | 原有笔记可列出、读取、搜索；B 发起的追加、覆盖可成功保存，并在后续窗口恢复 |
| history | A 与 B 两阶段产生的历史均可列出窗口、列出条目、按返回的窗口/条目 ID 读取及搜索；不能只保留最近一次重放到 B 的窗口 |
| 会话与命名空间 | 保持客户端逻辑会话、agent 名称及笔记路径的含义；不能因换号让同名路径指向另一份空笔记 |
| 生命周期 | 换窗口、压缩或重启网关后仍能找到正确状态；不依赖某一次请求中的偶然缓存或旧工具结果 |
| 失败与写入 | 失败如实报告；notes 写入结果不明时不盲目重放，不用空结果或静默删内容伪装成功 |

入口仍须遵守 Key 授权与账号资格。推理额度耗尽、原账号认证失效、账号被删除或撤权是不同情况，需要分别验证和说明，不能互相替代结论

## 不能作为完成依据的结果

- 模型切到 B 后继续回答，但没有实际访问旧 history/notes
- 把旧对话、旧工具输出或待恢复内容塞入新请求，再让模型复述
- 把待恢复的历史内容预先复制进 notes，只证明 notes 可读而没有验证 history
- 禁用 history/notes，退回普通 API 接入或仅靠摘要继续
- 删除不兼容的加密消息或 compaction 项后请求成功，却没有证明原状态仍可恢复
- 同一会话永远固定 A，A 耗尽后停止，只让新会话使用 B
- HTTP 200、存在 `encrypted_output`、单元测试通过或接口路由可达

当前有效上下文重放可以是恢复流程的一部分，但不能替代原生存储访问的验证

## 当前实现与剩余边界

`session_pool` 的会话在首次认领后保持粘性 owner，模型与会话级辅助请求跟随同一账号；只有已托管会话在 owner 被确切判定额度耗尽时才迁移。为避免这条约束变成“换号即丢状态”，实现选择在网关侧保存状态：

- history 由 CPRS 采集并用本地 PostgreSQL 回答四个官方工具，托管会话的检索查询词由网关在出站时适配成明文声明，客户端不改
- notes 仍由上游执行，CPRS 保存每个会话的原始加密 write/append 操作与 seq；owner 被确切判定额度耗尽时，先在新域按序重放并发布，之后才向新账号发送模型请求
- 能力默认关闭，需要在 `openai.codex_state_storage_enabled` 打开后新会话才进入托管；已托管会话在关闭时不倒退回官方域

细节与时序见[架构说明](codex-native-state-continuity-plan.md)，接口行为见 [API 参考](api.md#原生-codex-入口)。以下边界属于当前实现事实，不是待修缺陷：

- legacy 会话（接入前已存在于官方云端、或来源无法证明从新建开始完整采集）保持原账号与原域，不迁移、不自动升级
- 只重放收到完整响应的 notes 写入；结果不明或未终结的操作让迁移如实失败，不重发 append、不伪造成功
- 搜索只覆盖可读明文投影；纯密文对象保留原对象但不可读、不参与匹配，网关不解密
- 单实例个人用法：不做多宿主接管、备份/PITR 与远端副本一致性恢复，也不提供旧官方归档的导入

编译、本地定向测试与个人用途真实核心链路已有运行证据；未覆盖的账号故障、回切及高级恢复场景不作为已验证能力，详见[验收报告](reports/codex-native-state-continuity-acceptance.md)

## 已有证据

[跨账号状态研究](reports/codex-native-cross-account-2026-10-20.md#3-实验方法与控制变量)区分了两项已有实测：

- B 使用自己的认证和同一 session_id，未能直接恢复 A 保存的 history/notes
- A 的 notes 后端返回的一份真实加密结果，原样交给 B 的模型后，B 成功恢复了合成测试内容

它们说明存储访问归属与模型消费工具结果不是同一个问题。当前实现按这两条结论分工：history 由网关自己保存并服务，
notes 保留上游执行、只把原始加密操作按序搬到新账号的新域，不做任何正文解密或密文伪造

上述直接 API 实验不替代官方客户端验收。个人核心链路的实际覆盖见验收报告，纯密文历史可读性仍受本地明文投影边界限制

## 个人用途验收范围

使用对应版本的官方客户端、至少两个不同上游账号和全新合成会话，不读取用户真实历史。将仅写入 notes 的标记与仅出现在早期对话历史的标记分开，判据使用不可猜测的合成值或等价可核对结果

| 步骤 | 必须取得的证据 |
| --- | --- |
| 1. A 建立状态 | A 写入 notes、产生独立的早期历史，并在同账号下读取成功作为正对照 |
| 2. 切换执行账号 | 保持同一客户端逻辑会话，记录推理从 A 切到 B；区分真实额度耗尽与测试注入的故障，不能混称实测 |
| 3. B 换窗恢复 notes | 官方换窗后通过 notes search/read 读取原笔记，恢复提示词不预填旧系数或期望答案，且在 history 检索前执行 |
| 4. B 维护原笔记 | 对原笔记追加一次并读回，结果不明时先读确认，不盲重发 append |
| 5. 重启恢复 | 仅重启隔离网关，保留 PostgreSQL 与同一逻辑会话；新窗口读取包含追加结果的笔记 |
| 6. history 恢复 | 再次换窗，通过四个 history 工具找回 A 的早期事实并回答新问题，不借 notes 提供答案 |

覆盖客户端实际使用的列表、读取、搜索、写入及窗口恢复行为；如使用父子 agent，还需核对对应命名空间。用例未覆盖的操作和故障状态单列，不把一次 notes.read_file 成功概括成全部能力通过

证据只保留脱敏的请求关联、执行账号/状态访问账号别名、调用动作、结果判定与必要的合成标记，不保存认证令牌、真实笔记、用户会话正文或要求模型披露私有推理

**完成标准：换号后的原生工具读写与恢复闭环通过，且明确其支持范围和失效边界。普通切号、同 owner 访问或当前窗口重放通过，都不能替代这一结论**

当前结论限于上述个人核心链路。B 阶段历史的独立恢复、B→A 回切、其他账号失效原因和多宿主恢复不在这次真实验收范围内；不声明已对所有 opaque 上下文来源完成形式化排除。具体证据和验证缺口见[验收报告](reports/codex-native-state-continuity-acceptance.md)
